# Student Data Inventory

This inventory uses source-code evidence only. It contains no real user data.

| Category | Collected where | Purpose | Storage | Access | Third parties | Retention/deletion | Controls/unknowns |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Teacher email | OAuth sign-in, teacher APIs | Account identity, class ownership, admin/activity tracking | `users.email`, `classes.owner_email`, `activity_events.email` | Teacher, admin page, server logic | Google/Microsoft OAuth, Turso, optional Resend | No account deletion implemented | Auth/session checks; support-access policy needed. Private Discord alerts receive only an irreversible HMAC reference, never the email. |
| Teacher name | OAuth session profile | UI greeting/auth display | NextAuth session/JWT, not custom DB | Signed-in user/session | Google/Microsoft OAuth | Session lifetime via NextAuth | Not stored in app DB by current schema. |
| Student name | Assignment submission form/roster import | Identify submissions and roster rows | `submissions.student_name`, `roster.student_name` | Assigning teacher, student dashboard for own submissions | Turso | Soft delete then hard delete for submissions; roster remains until class/roster deletion | Student can type any name; email is stronger identity. |
| Student email | OAuth session, submission route, roster import | Authenticate submissions, rate limit, roster, dashboards | `submissions.student_email`, `roster.student_email`, `users.email` | Assigning teacher, student, admin aggregate views | OAuth provider, Turso, Upstash for submission limits | Submission rows hard-delete after soft-delete window; users/roster retention gaps | Optional domain and roster gates. |
| Class names/membership | Teacher class/roster UI | Organize assignments/students | `classes`, `roster` | Owning teacher, admin page | Turso | Class soft-delete then hard-delete after 30 days; roster cascades with class hard delete | No district-level admin role. |
| Assignments/instructions | Teacher assignment UI | Student prompt and grading context | `assignments` | Public assignment details omit owner email; teachers see owned assignments | Turso; attachment files in Vercel Blob | Assignment soft-delete then hard-delete after 30 days | Assignment links are bearer-style public links requiring student sign-in to submit. |
| Uploaded attachments | Assignment create/edit | Student directions/supporting materials | Private Vercel Blob pathname, or a legacy public URL pending migration, plus assignment fields | Owning teacher and signed-in students allowed by the same assignment-access policy, through a protected proxy | Vercel Blob | Cleanup deletes unreferenced hard-deleted assignment attachments | New uploads are private; the guarded migration must prove that no legacy public worksheet objects remain. |
| Audio recordings | Student browser recorder | Speaking submission review | Private Vercel Blob pathname, or a legacy public URL/data URL pending migration | Authorized teacher/student audio routes | Vercel Blob; Turso for legacy data URLs | Blob delete at hard-delete cleanup; legacy DB data deleted with row | New uploads fail closed to private storage; the guarded migration must prove that no legacy public audio objects or DB-held audio remain. |
| Grades/rubric scores | Teacher grading UI | Classroom grading | `submissions.grade`, `submissions.rubric_scores` | Teacher, student dashboard for own data | Turso | Deleted with submission hard-delete | No audit history yet. |
| Written feedback | Teacher grading UI | Student feedback | `submissions.feedback` | Teacher, student dashboard for own data | Turso | Deleted with submission hard-delete | Max length validation. |
| Submission timestamps | Submission creation | Ordering, exports, student history | `submissions.submitted_at` | Teacher, student, CSV export | Turso | Deleted with submission hard-delete | No separate retention policy. |
| Auth identifiers/cookies/session | NextAuth | Authentication | NextAuth JWT/session cookies | User/browser, server | OAuth providers | Session lifecycle via NextAuth | Cookie settings should be verified in deployment. |
| IP addresses | Rate limiting | Abuse prevention | Upstash rate-limit keys for auth/feedback by IP | Server/provider | Upstash | Provider retention unknown | No app DB storage. |
| Activity logs | Sign-in/teacher/class/assignment events | Founder analytics | `activity_events` | Admin page | Turso; separate typed Discord lifecycle alerts use only irreversible internal references and safe counts | No automated deletion | Database rows contain emails; retention decision required. |
| Support/feedback messages | `/feedback` | Support and TryHabla for Schools contact | `feedback_messages` | Admin page and optional Resend email | Turso, Resend; an explicit TryHabla for Schools submission may send only an irreversible lead reference and protected admin path to private Discord | Admin can delete; no auto retention | Generic feedback never triggers Discord; messages, organization names, personal names, emails, and roles are never included in Discord payloads. |
| Admin analytics | `/admin` | Founder operational view | Derived from DB tables | `ADMIN_EMAIL` only | Turso | Follows source table retention | Verify production admin email and access. |
| AI transcripts and generated grading data | Optional teacher-requested transcription and grading | Standalone transcripts and optional grading assistance | `submission_transcripts` stores the durable transcript and transcription metadata; `ai_grading_attempts` stores optional suggestions, evidence, model/provider metadata, status, and safe error classification | Assigning teacher through authenticated routes | OpenAI or another configured provider if enabled; Turso for persistence | Deleted when the related submission is hard-deleted; no shorter AI-specific TTL currently | AI is gated by deployment configuration and teacher action; retention, disclosure, provider data controls, and school authorization still require review. |
| User-directed Google Drive exports | Teacher chooses a transcript or original recording and starts an export | Place a teacher-selected copy in a clearly named TryHabla folder in the teacher's or school's Drive | A short-lived Google access token is held only in browser memory; TryHabla stores no Google Drive refresh token and no additional durable copy for the export | The initiating teacher and the Google account they authorize | Google Drive, using only `drive.file` | The exported copy persists independently under the Google account's policies until an authorized Drive user deletes it; TryHabla deletion does not remove it | Disabled unless `GOOGLE_DRIVE_EXPORT_ENABLED=true`; the teacher or school must be authorized to export the selected student content. TryHabla does not promise permanent storage. |
